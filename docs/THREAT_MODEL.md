# Tooling trust boundaries

Current assets are maintained source, exact metadata/schema/lock identities and scoped infrastructure reports. Reviewed executable policy and its independently pinned schema are trusted. Received JSON cannot choose an executable, repository identity, plugin or weaker policy.

The implemented input boundary refuses duplicate keys, nonfinite values, invalid UTF-8, unpaired surrogates, oversized files and linked/nonregular inputs. Fixed authored diagnostics avoid echoing confidential values. Accepted metadata precedes exclusive output creation; verification never replaces an inventory.

The tooling assumes a stable ordinary local filesystem and reviewed environment. It does not sandbox hostile concurrent filesystem changes, operating-system compromise or power loss. Static checks do not establish field-report accuracy, source qualification, complete inventory, current health or recall completeness.

Future reports require actual minimized source provenance, signed unit/pack context, supported aggregate methods, freshness and complete expected coverage. A valid seal cannot supply absent units, convert a proxy into measured accuracy or authorize rollback. Quarantined, stale and conflicting observations remain visible. Raw capture stays in its separate authorized lane.
